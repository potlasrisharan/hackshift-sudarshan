# Triage Sentinel

Status: engineering demonstration; synthetic knowledge base, not clinically
calibrated triage. The current implementation has four illustrative latent classes
and seven binary/unsure symptoms. This is smaller than the target clinical model.

**Problem:** choose informative questions without allowing an LLM to determine
urgency. A fixed list wastes interactions; free text generation is not auditable.

Inputs/outputs are validated by sentinelInputSchema. For class c and answers E,
`log w(c)=log prior(c)+Σ log likelihood(answer|c)`. Subtract the largest log weight,
exponentiate and normalise. Unsure contributes no likelihood. Next question
maximises `H(C)-P(yes)H(C|yes)-P(no)H(C|no)`, after mandatory danger screens.
An affirmative chest-pain, breathlessness or fainting screen returns emergency;
otherwise the output always requests clinician review, never establishes safety.

```text
validate answers against closed ontology
compute stable log-space posterior
if any affirmative danger screen: return emergency and stop
ask first unanswered danger screen
otherwise evaluate each unasked question's expected information gain
return highest-gain question, posterior and explicit uncertainty
```

Data structures: dense class×symptom likelihood matrix and partial answer map.
Complexity O(CS) time and O(C+S) extra space. Tunables: illustrative priors and
likelihoods. No fitted clinical thresholds or calibrated confidence interval is
claimed. Browser/Node transcendental math compares with 1e-10 numeric tolerance.

Edge cases: unknown symptom IDs and invalid answers fail validation; unsure is
neutral; log-space prevents underflow; all-no still requests clinical review;
confirmed danger always escalates regardless of other evidence. Paediatrics,
pregnancy and full complaint-specific screening are not clinically supported.

Verification: tests/engine.test.ts checks normalisation, unsure neutrality and
monotone red-flag escalation; tests/safety.test.ts covers all three danger flags;
browser test verifies the red-flag display and equality with API output. Real
latency is generated by scripts/bench.ts. No top-k diagnostic accuracy claim.

60-second explanation: “The demo asks danger questions first, then uses
probabilities to choose a question that reduces uncertainty. Its numbers are
illustrative; a clinician still reviews every result.”

Technical explanation: “Stable naive-Bayes posterior and expected-information-gain
selection operate on a closed ontology. A separate monotone danger override can
only escalate. Current priors are synthetic; asymmetric clinical loss,
calibration, a reviewed ontology and subgroup evaluation remain required.”
